# Santo Copilot v1 — Intent Routing, Evidence, Quota and Acceptance

> **Design specification only — NOT deployed.** Issue #73. Preserve existing Phase 7–10 RAG, citations, quota and conversation contracts until separate implementation is verified.
> A user should not select a mode manually. The server should route intelligently and conservatively.

## 1. Target interaction lifecycle

```text
Authenticated host -> Santo session / tenant status / entitlement check
  -> input validation + rate limits + active exam/access policy
  -> bounded validated context + deterministic urgent safety check
  -> conservative intent router (short message + approved conversation context)
    -> deterministic greeting / acknowledgement / off-topic redirect
    -> non-factual clarification or study-navigation response
    -> evidence-grounded medical tutor / question explanation -> AI Search
       -> bounded retrieved passages -> Workers AI model adapter
       -> strict structured response -> trusted citation validation -> source snapshot
       -> atomic quota finalization -> validated response
  -> persist authorized turn safely (with exact idempotency semantics)
```

**No bypass:** Authenticate and authorize tenant/user before any branch, including free greetings. Evaluate exam disclosure and abuse limits before choosing a cheaper route. A route suggestion generated by an LLM is untrusted and may never authorize a different user, reveal an explanation, or decide charging by itself.

## 2. Route taxonomy and priority

| Priority | Route | Examples | Allowed behavior | AI Search / medical citations | Default usage proposal |
|---|---|---|---|---|---|
| 0 | urgent_safety | I have severe chest pain right now / طفلي مش قادر يتنفس | Brief general emergency direction; encourage local emergency services/urgent professional care; no diagnosis | No required wait for RAG; do not manufacture citations | 0 units for deterministic safety text, rate limited |
| 1 | exam_restricted | Answer this active timed exam question / اديني إجابة السؤال في البلوك | Refuse prohibited answer or hints; offer allowed later review or generic study navigation | Never retrieve prohibited stem/explanation | 0 units if deterministic restriction |
| 2 | greeting_ack | hi / شكرا / صباح الخير | Short warm response, invite medical study question | No search; no citations | 0 units for fixed template, rate limited |
| 3 | off_topic | Write a Python scraper / أخبار الدوري | Briefly redirect to medical education | No search; no citations | 0 units for fixed template, rate limited |
| 4 | clarification_coaching | I don't know where to start studying / مش عارف أنظم مذاكرتي | Ask useful clarification or share generic study strategy without medical facts or invented personal history | No search only if no medical factual claims | Fixed template 0; if generative model is needed, metered explicitly |
| 5 | medical_grounded | Explain STEMI / compare beta-blockers / analyze this released MCQ | Retrieve allowed medical evidence; synthesize with verified citations and uncertainty | Required; citations server-verified | 1 unit for successful validated turn as current Santo policy |

### Ambiguous and mixed messages

- In mixed messages (Hi, explain heart failure) the substantive medical request wins: choose medical_grounded rather than greeting_ack.
- A short follow-up (Why? / ليه؟) must resolve only against tenant/user-authorized, previously verified conversation context. If context is insufficient, ask what the learner means; do not improvise clinical explanations.
- If a request includes study planning **and** medical claims, use medical_grounded for the factual portion, or split into a brief coaching reply that asks what to explain next. Do not present unsigned facts as generic coaching.
- When routing is uncertain between conversational and medical, fail toward medical_grounded or ask for clarification; never turn missing evidence into uncited medical explanations.
- Intent classification is **not an authority system**. Server must independently validate request, session, library IDs, exam permissions and availability of allowed resources.
- Do not allow untrusted retrieved text to alter route, billing, resource access or system instructions.

## 3. Quota and replay policy (future design; no meter changes yet)

- **0 unit deterministic routes:** greeting_ack, off_topic, standard clarifications, explicit exam restriction and urgent_safety can be answered from vetted localized templates. No provider/model call and no quota reserve/finalize. These are subject to per-user/IP rate limits, tenant access checks and anti-spam controls, and should be persisted only if within authorized conversation policy.
- **Generated study coaching:** if it requires an LLM, treat it as a metered invocation (default proposed one unit) until an independently approved pricing/usage contract exists; it must not masquerade as a free template call.
- **medical_grounded:** keep current authoritative TenantMeterDO reserve -> AI Search -> model -> citation validation -> finalize (one successful unit). On pre-finalization evidence/model failures release the reservation; do not tell users it was charged without observing finalization.
- **Never leak billing policy via model instructions.** Route and unit cost are decided by server configuration, not by user prompts or tenant widget.
- Idempotency for generation: preserve exact user + tenant + conversation + client idempotency + query + library scope semantics, and maintain the existing finalization/replay behavior. Do not create a new key on network retry. Any zero-unit deterministic response still needs a stable replay identity if persisted.
- Tenant-wide and individual quota limits, suspension, and entitlement checks are still authoritative and separate. Proposed deterministic free responses do **not** imply suspended users can continue using a protected tenant widget.

## 4. Evidence, citations and absence of content

- Existing retrieval uses a global Santo library catalog and optional validated library filter. All Libraries by default. Library selection is a **search filter, never tenant permission**.
- For substantive medical teaching, require evidence from actual retrieved passages, source IDs, and independently validated citation metadata. The LLM cannot invent reference titles, URLs, document locations or images.
- No evidence: do not call the model on an empty retrieval list; return a user-friendly, localized message in the widget (e.g. 'I couldn't verify this from the available medical sources yet. Try a specific concept or another library.'). Never imply the source contains content it does not.
- **Current reality:** the backend returns HTTP 422 with INSUFFICIENT_EVIDENCE. Friendly user-visible behavior is a **future** widget/API mapping and must not be advertised as implemented.
- Weak or contradictory evidence: model may say what cannot be established and ask a targeted clarification. Never fabricate to satisfy a citation requirement. A missing citation means the medical answer cannot succeed.
- Keep R2 verified source snapshots tenant/user/message-scoped; no source references from older chats may be claimed as new evidence without authorized retrieval.
- Do not reduce strict citation validation or reveal provider-draft text before validation. Streaming remains buffered and server-validated until a separately tested new contract exists.

## 5. Trust, exams and student data

**Trusted server-only inputs** should be generic, schema-validated platform capability flags, approved locale, learner authorization, signed resource references, actual exam status, review permission and permitted course metadata. The widget may request a context but cannot declare its own permissions.

- For timed/live exams: never reveal restricted correct answer, explanation, distractor analysis, targeted elimination hints, or protected reference ranges. If the active question cannot be securely identified, do not attempt to solve a possibly active item pasted into chat.
- Post-exam review: authorize question membership and released answers in the host backend first; then allow question-by-question teaching on available verified materials. A generic Santo tenant API key alone does **not** permit access to customer question DB.
- For study coaching: authorized performance info should be passed in minimized aggregated form only after explicit platform authorization; without it, use conditional language ('if this is difficult for you') instead of asserting weak areas or scores.
- Personal patient or medical history, optional student progress, private notes and files must not be silently sent to providers or routine telemetry. Store only required tenant/user scoped data; obtain the appropriate host permissions and privacy controls.
- Customer-branded context must remain configuration, never a custom prompt fork that disables universal safety/citations.

## 7. Implementation slices and acceptance gates

1. **Implementation issue/PR A:** typed intent outcome contract and conservative router behind a disabled-by-default feature flag. No customer-specific logic. Validate mixed-language examples and prompt injection. Add telemetry only for route/latency/error code, not message text.
2. **PR B:** deterministic greeting/off-topic/clarification/urgent-safety templates and server-owned exam restrictions before retrieval. Bind auth, rate-limit, session order, persistence and idempotency. Prove no unintended model calls, quota bypass or content disclosure.
3. **PR C:** implement versioned core prompt assembly with approved host context for medical_grounded (preserve strict existing buildGroundedPrompt constraints); keep existing Workers AI adapter until explicitly replaced. Add response formatting that does not leak raw error codes to end users.
4. **PR D:** controlled rollout to one pilot test tenant in Staging only, compare existing RAG on real licensed medical sources, cite accuracy, QA on bilingual turns and denied exam disclosures, and run deterministic failure/retry tests. Obtain user approval before broad enablement.

Required CI cases: cross-tenant access; unsigned/synthetic host context; active/finished exam modes; ambiguous follow-up; mixed-intent routing; medical sources missing; hallucinated sources; same-key retries; account suspension; 429 quota; no charge on pre-finalization failure; validated buffered streaming; injection in medical source/user turn; language adaptation and data-minimization. Maintain exact-head Verify, post-merge Verify and real staging browser evidence before calling the feature live.
